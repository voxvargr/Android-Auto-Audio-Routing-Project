- 14:58:00.375: Telecom requested voice-communication focus for the call.
- 14:58:01.445: the system entered MODE_IN_CALL.
- 15:05:36.408: Telecom released focus, consistent with a call lasting about

AAARP auto-log during the Google interaction:

- currentRoute=NX809J - Earpiece - output.
- AAARP repeatedly logged stage=route_skipped_generic_sco because Android exposed

    A2dpSuspended=false
    setBluetoothA2dpOn(true)=ok
- AAARP did not log a SCO clear, route reassert, or
  "Bluetooth SCO route paused during media playback" during this incident.
- Once MODE_IN_CALL began, AAARP correctly cleared its call-sensitive media
  effects/mute and logged that it left the route alone.

Microphone evidence:

- The original saved diagnostic hit its 32K cap before the August 11 recording
  history, so that file alone cannot identify the microphone.
- A live read-only query of the full retained history found no 14:57 Google,
  Gearhead, or VOICE_RECOGNITION recording event.
- At the 14:57:52 AAARP root snapshot, Recorder port map was empty, vendor
  IsRecording flags were false, and the microphone was not muted.
- Google app RECORD_AUDIO app-op had no access time near the incident; Gearhead
  also had no access time near it.
- The later phone-call capture was inconsistently represented in Android's
  recording ledger, so absence from that ledger is not absolute proof that no
  audio existed. Android Auto can also have a head-unit/remote capture path that
  is not represented as a normal phone-side AudioRecord.

Best-supported interpretation:

- Google reached the spoken reply workflow, but the evidence favors "no usable
  Assistant listening/capture path was established" over "Google captured the
  OpenDots microphone and merely misunderstood the words."
- The working call proves the Telecom/HFP call path and its microphone worked.
  It does not prove the separate Assistant/Android Auto capture path worked.
- AAARP did not explicitly select a microphone during the reply. Its one plausible
  indirect interaction was restoring/pinning A2DP during the exchange, which can
  work against the SCO/voice transition needed by some headsets.
- This is a strong hypothesis, not a proven root cause. A controlled A/B test is
  still required.

3. SUGGESTED DESKTOP PATCH
==========================

The desktop working tree now contains a conservative patch to transplant by
reviewing the diff, not by replacing the laptop files wholesale.

A. Assistant/guidance routing guard

File:
  app\src\main\java\dev\voxvargr\aaarp\RoutingMonitorService.java

- Registers AudioManager.AudioPlaybackCallback on Android 8/API 26 and newer.
- Detects USAGE_ASSISTANT and the incident's
  USAGE_ASSISTANCE_NAVIGATION_GUIDANCE playback.
- Holds a 12-second elapsed-time grace after playback ends so the guard spans the
  observed silent listening gaps.
- Keeps call/ring/communication protection at higher priority.
- While guarded, AAARP stops making new SCO/A2DP routing changes and suspends only
  its media-strategy/A2DP pin (including the Gearhead focus block).
- It deliberately does not clear an existing communication/SCO route because that
  route may already be the desired OpenDots microphone.
- After the guard, it restores only the media pin it suspended.
- Stop/disconnect cleanup clears the media role whether it is active or marked
  suspended, avoiding a leaked root media role if an async clear failed.
- Adds throttled "assistant audio guard" auto-log entries.

Known limitations:

- Detection is usage-based, not package-based. Normal Maps/Waze navigation speech
  can conservatively trigger the same 12-second yield.
- A Gemini/Assistant implementation that labels all output MEDIA or UNKNOWN could
  be missed.
- The patch yields AAARP interference; it cannot guarantee Android Auto will pick
  OpenDots rather than the head-unit microphone.
- The 12-second value covers this incident's roughly 8.5-second gaps but needs a
  real-device A/B test.
- Android below API 26 keeps the old behavior.

B. Diagnostics prioritized for voice failures

File:
  app\src\main\java\dev\voxvargr\aaarp\RootShell.java

- Puts recent recording activity and current AudioPolicy input clients before
  large focus/policy dumps so they survive the 32K Java output cap.
- Captures the current focus stack separately from a bounded recent focus history.
- Keeps the last/top focus owner on deep focus stacks.
- Adds installed package timestamps, base APK path, and base APK SHA-256.
- Replaces oversized stale Wi-Fi history with bounded current-only Wi-Fi evidence.
- Applies the same priorities to periodic auto-log root snapshots.

The revised shell commands were executed read-only against the phone:

- Manual diagnostic shell: exit 0, about 626 ms. Important sections appeared
  before the 32K cap.
- Auto snapshot: exit 0, about 452 ms, about 26.6K characters, fully under cap.

C. Non-root installed-build identity in saved diagnostics

Files:
  app\src\main\java\dev\voxvargr\aaarp\BuildIdentity.java
  app\src\main\java\dev\voxvargr\aaarp\MainActivity.java

- Saved diagnostics now include package/version, first-install and last-update
  times, and SHA-256 of the app's installed base APK.
- This works without root and prevents two different 0.1.0/code-1 APKs from being
  mistaken for each other.
- An APK hash identifies the exact artifact, not its source commit. Record the
  laptop's HEAD, dirty diff, and built APK hash together. A generated Git SHA/dirty
  BuildConfig field would be a useful later improvement.

These edits were intentionally NOT compiled on this desktop because the source is
not the phone's authoritative GPS-capable tree.
