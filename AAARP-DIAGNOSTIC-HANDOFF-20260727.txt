Most likely cause of the terrible ringer
----------------------------------------
Confidence: high. The live automatic AAARP log captured the incoming T-Mobile DIGITS
event even though the attached manual diagnostic did not.

Approximate event timeline on 2026-07-27:

15:49:06  T-Mobile DIGITS gains audio focus and the current communication route changes
          from the earpiece to a generic Bluetooth SCO device.
15:49:07  AAARP reports routeActiveForTarget=false, but starts issuing
          "Bluetooth SCO route paused during media playback" and reasserts Bluetooth
          A2DP (A2dpSuspended=false and setBluetoothA2dpOn(true)).
15:49:07-15:49:34
          AAARP repeats the SCO-pause operation about five times while the phone is
          ringing / DIGITS owns audio focus.
15:49:13  AAARP finally clears its global media LoudnessEnhancer.
15:49:38  DIGITS releases focus and the preceding audio owner regains it.

The installed APK's behavior explains this sequence:

1. Its generic-SCO fallback guard checks only whether the generic SCO device is
   unmatched and whether AudioManager mode equals MODE_IN_CALL.
2. It does not treat MODE_RINGTONE or MODE_IN_COMMUNICATION as call-sensitive states.
   T-Mobile DIGITS/VoIP-style calls commonly use MODE_IN_COMMUNICATION instead of
   MODE_IN_CALL, and ringing may use MODE_RINGTONE.
3. pauseBluetoothScoRouteForMediaIfNeeded() can clear the current SCO route merely
   because the current communication device is SCO, even when
   routeActiveForTarget=false. In other words, AAARP can interfere with a route owned
   by the phone/call app rather than a route that AAARP itself selected.
4. clearRoute() calls clearCommunicationDevice() and then forces AudioManager mode to
   MODE_NORMAL. Forcing NORMAL during ringing/communication is particularly risky.
5. The newer APK applies a session-0 LoudnessEnhancer at +1200 mB (roughly +12 dB).
   It uses a 15-second "recently had media playback" grace period, so this global
   effect remained enabled for the first several seconds of the incoming ringtone.
   A strong session-0 boost can clip/distort a loud ringtone.
6. AAARP was also trying to keep/reassert A2DP during the same call transition.

The ugly ringer was therefore probably a combination of the global +12 dB effect and
AAARP repeatedly fighting the call's SCO/mode transition. The call being unanswered
does not prevent the problem because the damaging transition happens while ringing.


Recommended repair order
------------------------

P0 - Recover and commit the actual July 24 source

Before making a release or installing a new APK, find the other PC's uncommitted/newer
files and merge them into this repository. Confirm the recovered source builds an APK
whose relevant classes/settings match the installed behavior.

P0 - Make every call/ringing/communication state untouchable

Create one clearly named predicate such as isCallOrCommunicationActive(). It should
at least treat all of these modes as protected:

* AudioManager.MODE_IN_CALL
* AudioManager.MODE_IN_COMMUNICATION
* AudioManager.MODE_RINGTONE

While protected, AAARP should not:

* clear or select a communication device;
* change AudioManager mode;
* pause SCO for media;
* pulse/reassert A2DP;
* apply media volume-floor changes;
* enable a global LoudnessEnhancer or DynamicsProcessing effect;
* perform playback-mute behavior intended for normal media routing.

Mode alone may not catch every OEM/call-app transition. Where practical, also use call
state, audio focus/playback configuration, or the root audio snapshot to detect ringing
and VoIP/DIGITS communication. Fail safe: if a call-like transition is ambiguous, leave
the system-owned route alone.

P0 - Only undo routes/state that AAARP owns

pauseBluetoothScoRouteForMediaIfNeeded() should not clear a device just because the
current communication device happens to be SCO. Only undo it when AAARP has explicit
ownership (for example routeActiveForTarget plus a recorded selected-device identity).

Likewise, do not force MODE_NORMAL unless AAARP previously changed the mode and has
recorded enough state to restore it safely. Prefer not changing global mode at all.
If mode changes remain necessary, track ownership and the previous mode, and never
restore over a call/ring/communication transition.

P0 - Release media effects immediately for calls

Do not carry the 15-second recently-playing grace period across a call-like event.
Disable/release the session-0 LoudnessEnhancer and DynamicsProcessing immediately when
ringing, in-call, or in-communication activity begins. Re-evaluate whether a +12 dB
session-0 boost is safe at all; it can affect more than the intended player and has a
large clipping risk. Prefer a smaller/configurable gain, an effect scoped to the actual
media session when possible, or volume-floor behavior without a global audio effect.

P1 - Fix the diagnostic export truncation

The attached AAARP-diagnostics-20260727-164147.txt contains only about 116 logical
lines. Large dumpsys Wi-Fi lines consume the output budget before later audio sections,
so the manual diagnostic missed the call evidence that existed in the auto log.

RootShell.MAX_OUTPUT_CHARS is 24000, but the loop checks the size before appending an
entire line. A single giant line can overshoot the cap. Fix by truncating each append to
the remaining character budget. Also put the short/high-value app, route, playback,
focus, mode, effect, and error sections before large dumpsys Wi-Fi text. State clearly
when any section is truncated.

P1 - Add automatic-log retention/rotation

Seven days of pulled auto logs totaled about 23,115,810 bytes. AutoLogWriter currently
has no obvious size cap or retention policy. Add per-file rotation and total retention
(for example a modest per-file cap plus 7-14 days or a fixed total-byte budget). Keep
the call-transition detail, but avoid indefinitely accumulating huge flattened root
snapshots.

P1 - Move/cache expensive monitoring work

The service's main-handler polling loop performs synchronous root/process/dumpsys work.
The active path also appears to query Android Auto/Wi-Fi state redundantly:
isAndroidAutoRunningWithRoot() already obtains current connection data and the service
then asks for it again. Run blocking probes off the main thread, cache a snapshot per
poll, and reuse it for all decisions/logging in that cycle. This should reduce latency,
battery use, and the chance of late route actions during fast audio transitions.

P1 - Fix the Android 6 comparator crash risk

Lint reports app/src/main/java/dev/voxvargr/aaarp/BluetoothDeviceCatalog.java around
line 92 using Comparator.comparing(), which requires API 24 while minSdk is 23 and core
library desugaring is not enabled. Replace it with an API-23-safe comparator or enable
and configure core library desugaring deliberately.

P2 - Clear the remaining lint errors

The current command produced 9 lint errors and 34 warnings. Important groups include
Bluetooth MissingPermission findings, diagnostics NewApi guarding/annotation, an
ACCESS_FINE_LOCATION declaration that also needs the appropriate coarse permission,
and WrongConstant findings that should be inspected to separate real issues from lint
false positives. Do not blanket-suppress these without reviewing the runtime path.
